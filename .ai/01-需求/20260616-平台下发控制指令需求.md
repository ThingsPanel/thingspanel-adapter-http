## 1. 背景与目标

### 背景

当前 thingspanel-adapter-http 适配器已经实现了设备上行链路（设备通过 HTTP POST 上报数据 → 平台），但平台向设备下发控制指令的链路**尚未实现**。

现状：
- `PlatformClient` 已定义 `CommandProcessorInterface` 和 `ControlProcessorInterface` 接口
- `PlatformClient` 已实现 MQTT 订阅逻辑（`startCommandSubscription`、`startControlSubscription`）
- 订阅消息的回调处理函数 `handleCommandMessage`、`handleControlMessage` 已写好
- 但**没有任何地方调用** `SetCommandProcessor` / `SetControlProcessor`，导致处理器从未被注入
- `HTTPHandler.SendCommand()` 当前直接返回 "HTTP protocol does not support async commands yet"
- **Bug**：源码 `startControlSubscription` 中订阅的 control topic 缺少 `plugin/{service_identifier}` 前缀，可能导致 control 消息收不到或多服务串扰（本次需求**附带修复**）

### 目标

在适配器中**完整打通**平台 → 适配器 → 设备的下行控制链路，使得：
- 平台通过 MQTT 下发 control/command 消息时，适配器能够接收并处理
- 适配器通过 HTTP POST 将控制指令主动推送给目标设备
- 设备下行地址优先从设备最近一次上报来源 IP 自动记录；`form_config.json` 中的 `host` 仅作为可选兜底配置（`commandUrl`/`controlUrl` 非必填有默认；`port` 非必填有默认 8080）
- 设备下行 HTTP 端口是目标设备自身监听端口，不是适配器 `server.port=19090` 或 `server.http_port=19091`
- 适配器不依赖设备主动拉取，采用主动推送模式
- 设备响应可被回传给平台（command 走 `command_response` topic）

---

## 2. In Scope（功能范围）

1. **MQTT 下行接收**：接收并处理平台通过 MQTT 下发的 `command` 和 `control` 消息（共 2 个 topic）
2. **设备 URL + Port 管理**：设备上报时记录来源 IP；通过 `form_config.json` 返回可选 host、2 个下行 URL、1 个 HTTP 端口配置，适配器按需加载
3. **HTTP POST 下发**：适配器使用 `net/http` 客户端向设备发起 HTTP POST 请求推送控制指令
4. **响应回传**：command 场景下，设备收到控制指令后的响应（带 `message_id`）需要回传给平台
5. **异常处理**：下发失败时记录日志，不阻塞后续消息处理
6. **附带修复**：control topic 前缀 bug

## 3. Out of Scope（不在本需求范围）

- 设备端 HTTP Server 的实现（由设备厂商负责）
- 控制指令的重试机制（超出本需求范围，后续迭代）
- WebSocket / MQTT 下行通道（适配器本身是 HTTP 设备专用，当前只用 HTTP POST）
- 设备认证方案（仅支持 `X-Api-Key`，由用户按需扩展其它方式）
- 第 3 个下行 URL 字段（已确认不实现；当前 SDK 也只有 2 个下行 topic）
- 设备 HTTP Server 路径冲突或路由隔离（由设备厂商负责）

## 4. 功能点与验收标准

### 功能点 1：平台 MQTT 下行消息接收

| 编号 | 功能描述 | 验收标准 |
|------|---------|---------|
| F1.1 | 适配器启动时注册指令处理器 | 调用 `platformClient.SetCommandProcessor()` 和 `SetControlProcessor()`，平台下发消息能被正确路由 |
| F1.2 | `handleCommandMessage` 消息处理 | 收到 MQTT `plugin/{service_identifier}/devices/command/{device_id}/{message_id}` 消息后，解析 method/params，调用 `ProcessCommand` |
| F1.3 | `handleControlMessage` 消息处理 | 收到 MQTT `plugin/{service_identifier}/devices/telemetry/control/{device_number}` 消息后，解析 payload，调用 `ProcessControl` |
| F1.4 | **附带修复** control topic 前缀 | `startControlSubscription` 改为 `fmt.Sprintf("plugin/%s/devices/telemetry/control/+", p.Config.ServiceIdentifier)`，与 command 保持一致 |

### 功能点 2：设备 2 个下行 URL + 1 个 Port 配置

| 编号 | 字段名 | 是否必填 | 默认值 | 说明 |
|------|--------|---------|--------|------|
| F2.1 | `host` | 否 | 最近一次上报 IP | 设备下行 HTTP 地址兜底配置，填 IP/域名，不填协议和端口 |
| F2.2 | `commandUrl` | 否 | `/api/v1/command` | Command 指令推送路径（相对路径） |
| F2.3 | `controlUrl` | 否 | `/api/v1/control` | Control 控制推送路径（相对路径） |
| F2.4 | `port` | 否 | `8080` | 设备 HTTP Server 监听端口 |

**URL 获取规则**：
- 适配器在设备上报 `/api/v1/uplink` 时记录来源 IP
- 设备 IP/域名优先使用最近一次上报 IP；若设备尚未上报，则从 `form_config.json` 的 `host` 字段兜底获取
- 设备下行端口从 `form_config.json` 的 `port` 字段获取，**未填时默认 8080**
- 该 `port` 是设备自己的 HTTP Server 端口；适配器 `server.port=19090` 只接收设备上报，`server.http_port=19091` 只接收平台回调
- 最终请求 URL = `{device_host}:{port}{commandUrl 或 controlUrl}`

**为什么同类多个设备只配一次相对路径**：
- 同一类设备共用同一份控制协议路径，配置一次即可全设备复用
- 不同设备只需在平台"设备管理"里配置不同 IP，路径保持一致
- 适配器只缓存"按 device_number → 配置项"的映射

**验收标准**：
- `form_config.json` 中增加 `host`（input，非必填）+ `commandUrl`/`controlUrl`（input，非必填）+ `port`（input，非必填但有默认值）4 个字段
- 适配器启动时加载 3 个字段到设备级内存缓存
- 用户未填时，3 个字段各自使用上表中的默认值

### 功能点 3：HTTP POST 下发控制指令（透传方案 B2）

**透传方案 B2**：在原始 MQTT payload 顶层**加 2 个 `tp_*` 字段**后透传，不重写消息体。

| 编号 | 功能描述 | 验收标准 |
|------|---------|---------|
| F3.1 | 构造 HTTP POST 请求 | 使用 `net/http` 构造 POST 请求，超时 10 秒 |
| F3.2 | 透传 JSON body | Command 顶层增加 `tp_message_id` 和 `tp_device_id`；Control 顶层增加 `tp_device_number`；原始 payload 保持不变 |
| F3.3 | 设备 URL 拼接 | 设备 URL = `device_host`（从设备注册信息） + `port`（从表单） + 相对路径（`commandUrl`/`controlUrl`） |
| F3.4 | 请求头 | `Content-Type: application/json`；`X-Api-Key: {device.AccessToken}` |
| F3.5 | 下发成功响应处理 | 收到设备 HTTP 2xx 响应后，触发 F4 回传流程 |
| F3.6 | 下发失败处理 | HTTP 请求失败（超时、连接错误、非 2xx）时，记录错误日志，不阻塞后续消息处理 |

**透传 B2 请求体示例**（Command 场景）：

```json
{
  "tp_message_id": "uuid-or-snowflake-id",
  "tp_device_id": "platform_device_id",
  "method": "switch_on",
  "params": {"switch": 1}
}
```

**透传 B2 请求体示例**（Control 场景）：

```json
{
  "tp_device_number": "D001",
  "values": {"switch": 1, "brightness": 80}
}
```

> **为什么 B2 而不是裸透传**：平台要求响应走 `command_response/{message_id}` topic，设备必须能在 HTTP 请求里拿到 `message_id` 才能正确回响应。B2 把 message_id 透传给设备，让设备能自己把 message_id 原样回给适配器。

### 功能点 4：指令响应回传

| 编号 | 功能描述 | 验收标准 |
|------|---------|---------|
| F4.1 | Command 响应回传 | 设备 HTTP 2xx 响应后，解析 body 中的 `message_id` 字段（设备必须回传），通过 MQTT 发布 `plugin/{service_identifier}/devices/command_response/{device_id}/{message_id}` 消息 |
| F4.2 | Control 不回传 | Control 是单向控制，**不回传**响应，仅记录日志即可 |
| F4.3 | 设备响应格式约定 | 设备 HTTP 响应 body 应为 JSON，包含 `message_id`（原值回传）和 `ok`（true/false）两个字段；其它字段忽略 |

**设备响应 body 示例**（Command 场景）：

```json
{
  "message_id": "uuid-or-snowflake-id",
  "ok": true,
  "data": { /* 设备可附加任意业务字段，适配器透传给平台 */ }
}
```

**适配器收到设备响应后，发布到平台的 MQTT 消息**（Command 场景）：

```
Topic: plugin/{service_id}/devices/command_response/{device_id}/{message_id}
Payload: {"ok": true, "data": {...}}
```

## 5. 数据流

### 下行控制流程

```
ThingsPanel Platform
    │
    │ MQTT: plugin/{service_id}/devices/command/{device_id}/{message_id}
    │ MQTT: plugin/{service_id}/devices/telemetry/control/{device_number}    ← 前缀 bug 已修
    ▼
PlatformClient (handleCommandMessage / handleControlMessage)
    │
    │ ProcessCommand(deviceID, messageID, CommandMessage{Method, Params})
    │ ProcessControl(deviceNumber, map[string]interface{})
    ▼
ControlProcessor / CommandProcessor
    │
    │ 1. Command 根据 deviceID 查 deviceNumber + device_host；Control 根据 deviceNumber 查 device_host
    │ 2. 查设备 commandUrl/controlUrl/port（从 formConfigCache）
    │ 3. 构造 HTTP POST 请求：
    │    - Command body: { tp_message_id, tp_device_id, ...原 MQTT payload }
    │    - Control body: { tp_device_number, ...原 MQTT payload }
    │    - header: X-Api-Key = device.AccessToken
    │    - url: http://{device_host}:{port}{commandUrl|controlUrl}
    ▼
HTTP 下发客户端 (http.Client, timeout 10s)
    │
    │ POST http://{host}:{port}/api/v1/command
    │ POST http://{host}:{port}/api/v1/control
    ▼
目标 HTTP 设备（接收并响应）
    │
    │ HTTP 2xx / 4xx / 5xx
    │ body: { "message_id": "xxx", "ok": true, "data": {...} }
    ▼
处理设备响应
    │
    │ 解析 message_id + ok
    │
    │ MQTT: plugin/{service_id}/devices/command_response/{device_id}/{message_id}
    │ payload: { "ok": true, "data": {...} }
    ▼
ThingsPanel Platform
```

## 7. 已确认问题（原 Q1-Q5 答案汇总）

| # | 问题 | 答案 |
|---|------|------|
| Q1 | 设备 URL 配置方式 | **只配相对路径**（同类设备共用），IP/域名从设备注册信息取 |
| Q2 | 设备 HTTP Server 默认端口 | **8080**（用户在表单填写，留空则用默认值） |
| Q3 | 控制指令 HTTP 请求体格式 | **方案 B2**：Command 在原 MQTT payload 顶层加 `tp_message_id` + `tp_device_id` 后透传；Control 顶层加 `tp_device_number` 后透传，不重写消息体 |
| Q4 | 设备 HTTP Server 认证 | **`X-Api-Key` header = 设备的 `Access-Token`** |
| Q5 | 第 3 个下行 URL 字段 | **不实现**（SDK 也只有 2 个下行 topic） |
