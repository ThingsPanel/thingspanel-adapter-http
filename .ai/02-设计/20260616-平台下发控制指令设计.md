# 详细设计：平台向 HTTP 设备下发控制指令

- **需求简称**: 平台下发控制指令
- **设计日期**: 20260616
- **状态**: 待确认
- **版本**: v1.1

---

## 1. 设计背景

本设计基于需求文档 `20260616-平台下发控制指令需求.md` v1.3，所有需求结论（Q1-Q5）均已落地。

### 本设计要解决的核心问题

1. `PlatformClient` 已有 MQTT 订阅逻辑，但 `SetCommandProcessor` / `SetControlProcessor` 从未被调用，消息处理链断裂
2. 需要将消息路由到设备 HTTP Server，但设备 IP/端口/路径/认证信息未统一管理
3. `startControlSubscription` 中 control topic 缺少 `plugin/{service_id}` 前缀（bug）
4. 需要与当前端口职责保持一致：适配器 `server.port=19090` 只接收设备上报，`server.http_port=19091` 只承载平台回调；平台下发控制不复用这两个端口作为设备下行目标端口。

## 2. 方案概述

### 2.1 整体架构

```
ThingsPanel Platform
    │
    │ MQTT: plugin/{service_id}/devices/command/{device_id}/{message_id}
    │ MQTT: plugin/{service_id}/devices/telemetry/control/{device_number}
    ▼
PlatformClient (MQTT subscription + bug fix)
    │
    │ SetCommandProcessor(processor)
    │ SetControlProcessor(processor)
    ▼
downlink.Processor  ← 新增包，实现 CommandProcessorInterface + ControlProcessorInterface
    │
    │ 1. GetDeviceByID(deviceID) → device.Host, device.AccessToken
    │ 2. DeviceAddressCache.Get(deviceNumber) → 最近一次上报来源 IP
    │ 3. DownlinkConfigCache.GetConfig(deviceNumber) → {host兜底, commandUrl, controlUrl, deviceDownlinkPort}
    │ 4. http.Client POST {device_host}:{deviceDownlinkPort}{url}
    │ 5. 设备响应回传 MQTT
    ▼
HTTP 设备（接收并响应）
```

### 2.1.1 端口职责边界

| 端口/配置 | 归属 | 职责 |
|---|---|---|
| `server.port`，默认 `19090` | 适配器 | 设备上报入口，只处理 `POST /api/v1/uplink` |
| `server.http_port`，默认 `19091` | 适配器 | 平台回调入口，只处理 ThingsPanel 平台回调和健康检查 |
| `deviceDownlinkPort`，默认 `8080` | 设备 | 设备自己的 HTTP Server 端口，用于接收适配器主动下发的 command/control |

下发控制链路不应该把控制消息 POST 到适配器的 `19090` 或 `19091`。`19090` 是设备到适配器的上行入口；`19091` 是平台到适配器的回调入口。适配器收到 MQTT 下发消息后，应作为 HTTP Client 主动请求目标设备自己的下行 HTTP 服务。

### 2.2 新增包：`internal/downlink`

按分层规范（`protocol` 不能引用 `platform`，但下行处理位于两者之间），新增 `downlink` 包：

| 文件 | 职责 |
|------|------|
| `config.go` | `DownlinkConfig` 结构体 + `DownlinkConfigCache` |
| `processor.go` | 实现 `CommandProcessorInterface` + `ControlProcessorInterface` |

`downlink` 包通过接口引用 `platform`，不直接引用 `protocol`。

### 2.3 数据流：完整时序

```
应用启动 (bootstrap/app.go)
    │
    │ 1. InitPlatformClient() → platformClient
    │ 2. NewDownlinkConfigCache() → configCache
    │ 3. NewDownlinkProcessor(platformClient, configCache) → processor
    │ 4. platformClient.SetCommandProcessor(processor)
    │ 5. platformClient.SetControlProcessor(processor)
    │   → MQTT subscription starts
    │
    ▼

[MQTT 下行消息到达]
    │
    │ MQTT topic: plugin/{service_id}/devices/command/{device_id}/{message_id}
    ▼
PlatformClient.handleCommandMessage(topic, payload)
    │
    │ Parse deviceID, messageID, CommandMessage{Method, Params}
    ▼
processor.ProcessCommand(deviceID, messageID, message)
    │
    │ 1. platformClient.GetDeviceByID(deviceID) → device
    │    · device.Host → deviceHost
    │    · device.AccessToken → apiKey
    │    · device.DeviceNumber → deviceNumber
    │ 2. configCache.Get(deviceNumber) → cfg{commandUrl, controlUrl, deviceDownlinkPort}
    │ 3. Build request body:
    │    {
    │      "tp_message_id": messageID,
    │      "tp_device_id": deviceID,
    │      "method": message.Method,
    │      "params": message.Params
    │    }
    │ 4. httpClient.Post()
    │    POST http://{deviceHost}:{deviceDownlinkPort}{commandUrl}
    │    Header: X-Api-Key: {apiKey}
    │    Header: Content-Type: application/json
    │    Timeout: 10s
    │ 5. 设备响应
    │    HTTP 2xx → parse body → {message_id, ok, data}
    │    → platformClient.PublishCommandResponse(deviceID, messageID, ok, data)
    │    HTTP non-2xx/timeout → log error, 不回传
    ▼
```

Control 消息按 `device_number` 路由：

```
[MQTT 下行消息到达]
    │
    │ MQTT topic: plugin/{service_id}/devices/telemetry/control/{device_number}
    ▼
PlatformClient.handleControlMessage(topic, payload)
    │
    │ Parse deviceNumber, controlData
    ▼
processor.ProcessControl(deviceNumber, controlData)
    │
    │ 1. platformClient.GetDevice(deviceNumber) → device
    │    · device.Host → deviceHost
    │    · device.AccessToken → apiKey
    │ 2. platformClient.GetDeviceAddress(deviceNumber) → 最近一次上报来源 IP
    │ 3. configCache.Get(deviceNumber) → cfg{host兜底, controlUrl, deviceDownlinkPort}
    │ 4. Build request body:
    │    {
    │      "tp_device_number": deviceNumber,
    │      ...原 MQTT payload
    │    }
    │ 5. httpClient.Post()
    │    POST http://{deviceHost}:{deviceDownlinkPort}{controlUrl}
    │    Header: X-Api-Key: {apiKey}
    │    Header: Content-Type: application/json
    │    Timeout: 10s
    ▼
```

## 5. 核心逻辑流程

### 5.1 Processor 设计

**职责**：封装下行指令的完整处理逻辑（获取设备信息 → 构造请求 → 发送 HTTP → 回传响应）。

**设计决策**：
- **不缓存配置**：每次下发时实时从平台查询 `GetDeviceConfig`，避免平台侧修改后插件缓存不一致的问题。
- **不回传不阻塞**：设备响应异常时只记录日志，不向上返回 error，以免阻塞 MQTT 消息处理。

**核心流程**：
1. `GetDeviceByID` 获取 `device.Host` + `device.AccessToken`
2. `GetDeviceConfig` 获取下行配置（commandUrl/controlUrl/deviceDownlinkPort）
3. 构造请求体，发送 HTTP POST
4. 设备响应 2xx → `PublishCommandResponse` 回传平台

```go
func (p *Processor) ProcessCommand(deviceID, messageID string, msg platform.CommandMessage) error {
    // Step 1: 通过 deviceID 查设备信息（获取 Host + AccessToken）
    device, err := p.platform.GetDeviceByID(deviceID)
    if err != nil {
        return fmt.Errorf("查设备信息失败: %w", err)
    }

    // Step 2: 查该设备的下行配置（实时查询，不缓存）
    devConfig, err := p.platform.GetDeviceConfig(deviceID)
    if err != nil {
        p.logger.WithError(err).Errorf("查设备配置失败: deviceID=%s", deviceID)
        return nil // 不阻塞，不回传
    }
    cfg := p.parseConfig(devConfig) // 从 DeviceConfig 中解析 commandUrl/controlUrl/deviceDownlinkPort

    // Step 3: 构造请求体（透传 B2：顶层加 tp_message_id + tp_device_id）
    body := map[string]interface{}{
        "tp_message_id": messageID,
        "tp_device_id":  deviceID,
        "method":        msg.Method,
        "params":        msg.Params,
    }
    bodyBytes, _ := json.Marshal(body)

    // Step 4: 拼接设备 URL
    deviceURL := fmt.Sprintf("http://%s:%s%s", device.Host, cfg.Port, cfg.CommandURL)

    // Step 5: HTTP POST（带 X-Api-Key header）
    req, _ := http.NewRequest(http.MethodPost, deviceURL, bytes.NewReader(bodyBytes))
    req.Header.Set("Content-Type", "application/json")
    req.Header.Set("X-Api-Key", device.AccessToken)

    resp, err := p.httpClient.Do(req)
    if err != nil {
        p.logger.WithError(err).Errorf("下发 Command 失败: deviceID=%s, method=%s", deviceID, msg.Method)
        return nil // 不阻塞，不回传
    }
    defer resp.Body.Close()

    // Step 6: 非 2xx → 记录日志，不回传
    if resp.StatusCode < 200 || resp.StatusCode >= 300 {
        p.logger.WithField("status_code", resp.StatusCode).Errorf("设备响应非 2xx: deviceID=%s", deviceID)
        return nil
    }

    // Step 7: 解析设备响应 body
    var devResp struct {
        MessageID string      `json:"message_id"`
        OK        bool        `json:"ok"`
        Data      interface{} `json:"data"`
    }
    if err := json.NewDecoder(resp.Body).Decode(&devResp); err != nil {
        p.logger.WithError(err).Warn("解析设备响应失败")
        return nil
    }

    // Step 8: 验 message_id，回传给平台
    if devResp.MessageID == messageID {
        _ = p.platform.PublishCommandResponse(deviceID, messageID, devResp.OK, devResp.Data)
    }

    return nil
}
```

### 5.2 ProcessControl 伪代码

流程与 `ProcessCommand` 相同，差异点：

| 差异 | ProcessCommand | ProcessControl |
|------|---------------|---------------|
| URL | `commandUrl` | `controlUrl` |
| 请求体 | `{tp_message_id, tp_device_id, method, params}` | `{tp_device_number, values}`（透传原始 controlData，不包含平台设备 ID） |
| 回传 | `PublishCommandResponse` | **不回传**（Control 单向） |

## 9. 风险与限制

| 风险 | 影响 | 应对 |
|------|------|------|
| 设备 HTTP Server 必须自己回 `message_id` | 如果设备不回 message_id，平台收不到响应 | 已在需求文档标注"设备响应格式约定"，设备厂商需遵守 |
| 下行 URL/Port 配置加载时机 | 如果设备在运行时新增加，下行配置缓存里没有 | 当前一次性加载；后续可改为懒加载 |
| 并发下发同一设备 | 多个指令同时下发到同一设备 | `http.Client` 内部有连接池，高并发场景需评估设备承受能力 |
| 设备 IP/域名从 `device.Host` 取 | 如果 Host 格式不对（如缺端口但自带端口） | 需要确认 `types.Device.Host` 字段的格式规范 |
| 下行设备端口和适配器端口混淆 | 把控制请求错误打到 `19090` 或 `19091` | 文档明确：下行目标是设备自己的 `deviceDownlinkPort`，不是适配器端口 |

### 待确认：Device.Host 格式

**已确认**：
- `Device.Host` = **纯 IP**（设备建立连接时获得，不含端口）
- 设备下行 URL = `http://{Host}:{deviceDownlinkPort}{commandUrl|controlUrl}`，其中 `deviceDownlinkPort` 和 `commandUrl`/`controlUrl` 来自设备下行配置。
- 适配器 `server.port=19090` 只接收设备上报；`server.http_port=19091` 只接收平台回调；二者都不是设备下行 HTTP Server 端口。

**form_config vs form_voucher 的区别**：

| 表单 | 作用域 | 内容 | 存储位置 |
|------|--------|------|---------|
| `form_voucher`（VCR） | 每设备独立一份 | `accessToken`（必填） | 平台按设备存储 |
| `form_config`（CFG） | 同类设备共用一份 | `host`、`commandUrl`、`controlUrl`、`port`（host 为可选兜底；路径和默认端口） | 平台按设备类型存储 |

**配置优先级**：
1. `accessToken` 从 `form_voucher`（VCR）取，每设备独立。
2. `host` 从 `form_config`（CFG）取作兜底；实际下发优先使用设备最近一次上报来源 IP。
3. `commandUrl`、`controlUrl`、`port` 从 `form_config`（CFG）取；URL/port 未填时使用默认值。

**SDK 数据来源**：平台 `GetDeviceConfig` API 返回的 `DeviceConfig` 字段包含 `form_voucher` 数据，`form_config` 为静态模板。`DownlinkConfigCache` 通过 SDK 按 deviceNumber 逐一加载。---
