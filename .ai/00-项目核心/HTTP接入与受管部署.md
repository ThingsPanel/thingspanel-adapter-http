# HTTP 接入与受管部署

## 当前已实现

HTTP 插件负责设备 HTTP 上报及 HTTP/长轮询下行，通过协议 SDK 查询平台设备、发送心跳，并经 MQTT 上报遥测、接收命令和返回回执。

- `server.port` 默认 19090：设备上报 `/api/v1/uplink`、poll 和 ack。
- `server.http_port` 默认 19091：平台回调及 `/health`、`/healthz`。不能把设备入口指向该端口。
- 设备使用 device_number，平台查询后解析为内部 device_id。保持原有载荷及上行 MQTT 契约。
- 当前依赖协议 SDK v1.2.6；平台客户端没有受管实例令牌配置与传递。当前代码还会打印整个 SDK 配置，受管改造须同步去除凭据日志。

代码入口：`internal/bootstrap/`、`internal/config/config.go`、`internal/platform/platform.go`、`internal/protocol/http_handler.go`。

## 已确认待完成：受管部署

20261112 用户已确认继续实施。下面是实施与验收约束，尚未表示已部署通过。

目标是在现有插件安装页面管理 HTTP 的安装、健康、启停及卸载，与 HA 共用 Agent 和官方签名目录。HTTP 保持协议插件类别，不能伪装成 HA 服务接入插件。

流程：官方源码构建并固定镜像摘要 → 官方签名目录登记 → 平台申请独立 HTTP 实例身份 → Agent 创建受限容器 → 注册协议回调及专用 MQTT 身份 → 通过受控设备入口接收数据。

关键规则：

1. HTTP 使用自己的身份和 MQTT 账号，不复用 HA、平台管理员或其他旧插件的凭据。受管令牌失效不得退回匿名兼容模式。
2. 现有平台共享身份的设备查询只接受相同租户；不能直接给共享 HTTP 使用空租户身份而宣称兼容。需明确增加安装实例与 HTTP 协议/设备范围授权，覆盖查询、列表、心跳、注册及 MQTT 范围；按实际安装状态生效。不得仅放宽空租户为任意设备。
3. 原有 HTTP 设备、模板和上下行契约保留。动态注册默认不由安装过程打开；如要启用，只能授权指定租户、指定模板，不分发全局模板密钥。
4. 当前 Agent 不允许容器直接绑定宿主端口。设备 19090 使用受控代理；平台回调 19091 仅内部可达。保留上报、poll、ack，代理超时支持长轮询。
5. 只用官方发布签名链，不替换信任根或手改线上签名目录。追加 HTTP 后保留原 HA 条目。
6. 新受管制品发布新版本，不让原 v1.1.1 标签悄悄代表不同代码。新容器通过健康与权限验证后再开放设备入口。失败保留原配置及可回退路径。
7. 对其他旧插件保留既有兼容路径；受管 HTTP 的接口无令牌、令牌过期/撤销、跨协议请求均需明确拒绝，不能依赖客户端自报协议名授权。

## 验收

- 安装页面出现 HTTP，安装/健康/停用/启用/卸载与实际容器状态一致，HA 持续正常。
- 独立测试租户 HTTP 温度上报入库；开关命令经长轮询取得、ack 返回，平台回执成功；保留已有直连下行能力。
- 无效身份、跨协议/越权设备、撤销及停用后访问失败；MQTT 仅允许自己的设备主题。
- 容器重启后恢复；设备入口不意外暴露平台回调；日志和公开制品不含凭据。

旧宿主机部署 Action 改为手动触发，避免源码推送重新启动已停止的旧服务；后续镜像发布使用 Dockerfile.managed。受管客户端沿用 SDK MQTT，仅对 SDK 不支持的受管 API 调用增加独立带身份的 HTTP 客户端，禁止重定向和匿名重试。受管模式不复用设备查询缓存，身份撤销后不能继续使用旧缓存上报。
